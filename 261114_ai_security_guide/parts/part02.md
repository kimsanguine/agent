# Part 2. 보안 기초 체력: 비개발자도 알아야 할 8가지 개념

> **🎯 학습 목표**
> - 8개 기본 개념(CIA, 인증/인가, 비밀 관리, 암호화, 입력 검증, 최소권한, 로깅, 안전한 기본값)을 자기 말로 설명한다.

3. 키·비밀번호는 어디에 두고, 누가 볼 수 있어야 하나?

## 2-1. 보안은 정확히 무엇을 지키는가? (CIA 3요소)

**Q.** 보안 사고라고 하면 "해킹으로 정보가 털리는 것"만 떠올리기 쉽다. 그게 전부인가?

**A.** 아니다. 보안은 세 가지를 지키는 일이고, 앞 글자를 따서 CIA 3요소라 부른다.

| 요소 | 지키는 것 | 비유 | 깨진 모습 |
|---|---|---|---|
| 기밀성 (Confidentiality) | 볼 자격 없는 사람이 못 본다 | 잠긴 서류함 | 고객 정보 유출 |
| 무결성 (Integrity) | 함부로 바뀌지 않는다 | 위조 방지 도장 | 주문 금액·권한 조작 |
| 가용성 (Availability) | 필요할 때 쓸 수 있다 | 영업 중인 가게 | 서버 다운, DB 삭제 |

**Q.** PM은 이것을 어디에 쓰는가?

**A.** 기능을 볼 때 "이 데이터가 새면(기밀성), 바뀌면(무결성), 멈추면(가용성) 각각 무슨 일이 생기나"를 3칸으로 묻는다. 답이 비어 있으면 아직 요구사항이 아니다.

> **🚫 흔한 착각** "보안 = 비밀 유지"가 전부다. 에이전트가 프로덕션 DB를 지우는 사고는 유출이 아니라 가용성·무결성 사고다.

**Q.** 바이브코딩에서는 어떻게 깨지는가?

**A.** AI는 "돌아가는 화면"을 목표로 만든다. 세 요소는 화면에 보이지 않으므로 요구하지 않으면 빠진다.

> **💡 PM 시선** 기능 명세서의 "인수 조건"에 CIA 한 줄씩을 넣는 습관이 가장 싼 보안 투자다.

> **🛠 실습** 우리 서비스의 핵심 데이터 3개를 골라 CIA 표를 채워 보자. 가장 아픈 칸이 첫 번째 보호 대상이다.

## 2-2. 누구인가, 해도 되는가? (인증 vs 인가)

**Q.** 로그인만 되면 안전한 것 아닌가?

**A.** 로그인은 "누구인가"를 확인하는 인증(Authentication)이다. "그 일을 해도 되는가"는 별개의 인가(Authorization)다. 호텔로 비유하면 인증은 프런트에서 신분증을 보이는 일, 인가는 그 카드키가 내 방만 여는지 확인하는 일이다.

**Q.** 세션, JWT, OAuth는 각각 무엇인가?

| 개념 | 한 줄 설명 | 흔한 실수 |
|---|---|---|
| 세션 | 서버가 "이 사람 로그인함"을 기억 | 만료 없음, 쿠키 보호 설정 누락 |
| JWT | 신원 정보가 담긴 서명된 출입증 | 서명 검증 생략, 긴 유효기간 |
| OAuth | 비밀번호 없이 "권한만 위임" | 필요 이상으로 넓은 스코프 요청 |

**Q.** 가장 흔한 사고는 무엇인가?

**A.** 인가 누락이다. 주소의 `/orders/1001`을 `/orders/1002`로 바꾸자 남의 주문이 보이는 식이다. OWASP Top 10 2025에서 1위(A01)가 Broken Access Control이다.

> **🚫 흔한 착각** "프런트 화면에서 버튼을 숨겼으니 막혔다." 인가는 반드시 서버에서 검사한다. 화면은 누구나 우회할 수 있다.

**Q.** 바이브코딩에서는 어떻게 깨지는가?

**A.** AI가 로그인 화면과 API를 빠르게 만들지만, "이 행이 이 사용자 것인가" 검사는 요청하지 않으면 생략하기 쉽다.

> **🧪 가설** AI가 만든 앱의 목록·상세 API 10개 중 상당수는 로그인 여부만 보고 소유자 검사를 하지 않을 것이다. 검증: 계정 A, B를 만들어 A의 ID로 B의 데이터를 요청해 본다.

## 2-3. 키와 비밀번호는 어디에 두는가? (비밀 관리)

**Q.** API 키, DB 비밀번호, 토큰은 왜 특별한가?

**A.** 이것들은 "열쇠 자체"다. 코드가 아무리 튼튼해도 열쇠가 공개되면 문을 열 필요도 없다. 클라우드 키가 유출되면 남이 내 비용으로 서버를 돌리거나 데이터를 읽을 수 있다.

**Q.** `.env`는 무엇인가?

**A.** 비밀을 코드와 분리해 보관하는 설정 파일이다. 원칙은 세 가지다.
1. 코드에 직접 적지 않는다(하드코딩 금지).
2. `.env`는 Git에 올리지 않는다(`.gitignore` 등록).
3. 운영 키는 배포 플랫폼의 시크릿 저장소에 넣는다.

```
# .gitignore
.env
.env.*
!.env.example   # 키 이름만 적은 견본은 공유
```

**Q.** 이미 올렸다면 지우면 끝인가?

**A.** 아니다. Git 이력과 복제본에 남는다. 유출된 키는 폐기하고 새로 발급(로테이션)하는 것이 정답이다.

**Q.** 바이브코딩에서는 어떻게 깨지는가?

**A.** 세 가지 경로가 흔하다. AI가 예시 코드에 키를 그대로 박는 경우, 채팅에 키를 붙여넣는 경우, 브라우저로 내려가는 프런트 코드에 서버 전용 키를 넣는 경우다. 에이전트가 `.env`를 읽을 수 있는 환경도 같은 문제다(Part 06~07에서 다룬다).

> **✅ 체크포인트** 키가 "브라우저에서 보이는 파일"에 있는가? 있다면 공개된 것으로 간주한다.

> **🛠 실습** 내 프로젝트에서 `sk-`, `key`, `token`, `password`를 검색해 코드에 박힌 값이 있는지 찾아 보자.

## 2-4. 암호화와 해시는 무엇이 다른가?

**Q.** "암호화했으니 안전하다"는 말은 충분한가?

**A.** 무엇을, 언제, 어떻게 보호하는지 물어야 한다. 암호화는 열쇠가 있으면 되돌릴 수 있는 잠금이다. 해시는 되돌릴 수 없는 지문이다.

| 구분 | 되돌리나 | 쓰는 곳 | 비유 |
|---|---|---|---|
| 암호화 | 열쇠로 가능 | 전송·저장 데이터 | 자물쇠 달린 상자 |
| 해시 | 불가 | 비밀번호 저장 | 문서의 지문 |

**Q.** 어디를 암호화하는가?

**A.** 두 구간이다. 전송 중(in transit)은 HTTPS/TLS로, 저장 중(at rest)은 디스크·DB·백업 암호화로 보호한다. 주소창의 자물쇠는 "통신 구간"만 보장하며, 서버에 저장된 데이터의 안전은 따로 확인해야 한다.

**Q.** 비밀번호는 어떻게 저장하나?

**A.** 평문이나 단순 해시가 아니라, 비밀번호 전용으로 설계된 느린 해시(bcrypt, scrypt, Argon2 등)에 솔트를 넣어 저장한다. 직접 만들지 말고 인증 서비스나 검증된 라이브러리를 쓴다.

> **🚫 흔한 착각** "직접 만든 암호화 방식은 남들이 모르니 더 안전하다." 암호는 직접 만들지 않는다. 검증된 표준만 쓴다.

**Q.** 바이브코딩에서는 어떻게 깨지는가?

**A.** AI가 오래된 예제를 따라 약한 방식(MD5 단순 해시, HTTP 호출, 고정 키)을 쓰거나, 로컬 테스트용 설정을 운영에 그대로 두는 경우가 있다.

> **🗣 토론** 우리 서비스가 저장하는 정보 중 "서버 운영자도 보면 안 되는 것"은 무엇인가? 그렇다면 암호화·해시 중 무엇이 맞는가?

## 2-5. 입력값은 왜 위험한가? (인젝션과 친구들)

**Q.** 사용자가 입력창에 쓴 글이 왜 사고가 되는가?

**A.** 프로그램이 "데이터"를 "명령"으로 착각할 때다. 식당 주문서에 "음식 하나, 그리고 금고를 열어라"라고 적었는데 주방이 그대로 따르는 상황이다.

| 이름 | PM 눈높이 설명 | 막는 원칙 |
|---|---|---|
| SQLi | 입력이 DB 명령의 일부가 됨 | 파라미터화된 쿼리 |
| XSS | 입력이 남의 브라우저에서 코드로 실행됨 | 출력 이스케이프 |
| CSRF | 로그인된 나를 속여 원치 않는 요청을 보냄 | CSRF 토큰, SameSite 쿠키 |
| SSRF | 서버를 속여 내부 주소를 대신 호출시킴 | 호출 가능한 주소 허용목록 |

**Q.** 취약한 모양은 어떻게 생겼나?

```
# 나쁜 예: 입력을 문장에 이어 붙임
query = "SELECT * FROM users WHERE id=" + user_input

# 좋은 예: 값 자리를 분리해 전달
query = "SELECT * FROM users WHERE id = %s"
db.execute(query, (user_input,))
```

**Q.** 바이브코딩에서는 어떻게 깨지는가?

**A.** 데모 코드는 문자열 이어 붙이기가 짧고 쉬워서 AI가 그 형태를 내놓기 쉽다. "입력은 서버에서 검증한다"는 요구가 없으면 화면 검사에만 의존한다.

> **🧪 가설** 요구사항에 "파라미터화된 쿼리 사용, 서버 측 입력 검증"을 한 줄 넣으면 AI 생성 코드의 위험 패턴이 줄어들 것이다. 검증: 같은 기능을 두 프롬프트로 생성해 코드를 비교한다.

> **💡 PM 시선** 입력 검증은 "막기" 기능이 아니라 "허용 목록 정의"다. 허용할 형식을 먼저 정하는 것이 기획 영역이다.

## 2-6. 권한은 얼마나 줘야 하나? (최소권한)

**Q.** 팀원에게 "일단 관리자 권한 줄까?" 하는 일이 편한데, 왜 문제인가?

**A.** 최소권한 원칙(Principle of Least Privilege)은 "일을 하는 데 필요한 만큼만" 주는 것이다. 건물 청소 직원에게 금고 열쇠까지 주지 않는 것과 같다. 사고가 나도 번지는 범위(폭발 반경)가 작아진다.

**Q.** 어디에 적용하나?

| 대상 | 최소권한 예시 |
|---|---|
| 사용자 | 본인 데이터만 읽기·수정 |
| 서비스 계정 | 읽기 전용 DB 계정 분리 |
| API 키 | 필요한 기능 스코프만 |
| 직원 | 퇴사·이동 시 즉시 회수 |
| AI 에이전트 | 파일·명령·네트워크 범위 제한 |

**Q.** 바이브코딩에서는 어떻게 깨지는가?

**A.** 막힌 에러를 풀려고 "관리자 키로 바꿔서 해결"하는 길이 가장 빠르기 때문이다. 에이전트에게 모든 파일과 DB와 명령을 열어 주면, 실수든 공격이든 한 번의 사고가 전체를 건드린다.

> **⚠️ 실제 사례** 2025년 5월 연구자가 Lovable로 만든 앱을 점검해 DB 행 단위 접근 제어(RLS) 정책이 없거나 약한 사례를 다수 보고했고, CVE-2025-48757로 등록되었다. 보고에 따르면 170여 개 앱의 303개 엔드포인트가 인증 없이 데이터에 접근 가능했다. 교훈: 기본적으로 "각 사용자는 자기 행만"이라는 최소권한 규칙을 DB 층에 명시해야 한다. 책임 범위(플랫폼 vs 사용자 설정)는 다툼이 있다: CVE 레코드에도 공급사가 이의를 제기했다고 명시돼 있다.

출처: NVD CVE-2025-48757 및 연구자 공개 내용(2025.5), 보안 매체 정리.

> **✅ 체크포인트** 이 키가 유출돼도 "읽기만" 가능한가? 아니라면 키를 분리한다.

## 2-7. 사고가 나면 무엇으로 확인하는가? (로깅·감사)

**Q.** 사고가 났는데 기록이 없다면?

**A.** 무슨 일이 일어났는지, 누가 했는지, 어디까지 번졌는지 알 수 없다. 로그는 건물의 CCTV와 출입 기록이다. 막는 장치가 아니라 "알아채고 되짚는 장치"다.

**Q.** 무엇을 남기고, 무엇은 남기지 않나?

| 남긴다 | 남기지 않는다 |
|---|---|
| 로그인 성공/실패, 권한 변경 | 비밀번호, 토큰 원문 |
| 데이터 삭제·내보내기 | 주민번호·카드번호 등 민감 정보 |
| 관리자·에이전트의 행동 | 개인정보 전체 덤프 |

**Q.** 데이터 드리븐으로는 무엇을 보나?

**A.** 로그인 실패율의 급증, 평소 없던 시간·지역의 접근, 대량 조회·다운로드, 권한 오류(403) 폭증 같은 지표다. 알림이 없으면 로그는 쌓이기만 한다. 2025 OWASP에서도 이 항목의 이름이 "Logging and Alerting Failures"로, 경고까지 포함한다.

**Q.** 바이브코딩에서는 어떻게 깨지는가?

**A.** 두 방향이다. 로그가 없거나, 반대로 디버깅용으로 요청 본문 전체(비밀번호 포함)를 찍어 둔다. 에이전트가 무엇을 실행했는지 기록이 없으면 사고 후 복기가 불가능하다.

> **🧪 가설** 에이전트의 명령·파일 변경 기록을 남기는 팀은 사고 원인 파악 시간이 짧아질 것이다. 검증: 모의 사고 시 원인 파악까지 걸린 시간을 비교한다.

> **🗣 토론** 로그에 "남겨야 하는 것"과 "남기면 안 되는 것"이 충돌하는 사례를 팀에서 하나씩 찾아 보자.

## 2-8. OWASP Top 10은 무엇을 말하는가?

**Q.** 웹 보안의 "가장 흔한 위험 10가지" 목록이 있는가?

**A.** OWASP Top 10이다. 최신판은 2025년판이며 항목은 아래와 같다(OWASP 공식 페이지 확인).

| 순위 | 항목 | PM 한 줄 번역 |
|---|---|---|
| A01 | Broken Access Control | 남의 것을 볼 수 있다 |
| A02 | Security Misconfiguration | 설정이 열려 있다 |
| A03 | Software Supply Chain Failures | 가져온 부품이 오염됐다 |
| A04 | Cryptographic Failures | 암호화가 없거나 약하다 |
| A05 | Injection | 입력이 명령이 된다 |
| A06 | Insecure Design | 설계 단계부터 빠졌다 |
| A07 | Authentication Failures | 신원 확인이 허술하다 |
| A08 | Software or Data Integrity Failures | 검증 없이 믿는다 |
| A09 | Security Logging and Alerting Failures | 알아챌 수단이 없다 |
| A10 | Mishandling of Exceptional Conditions | 예외 처리가 허술하다 |

**Q.** 2021판과 무엇이 달라졌나?

**A.** 공급망 항목(A03)과 예외 처리 항목(A10)이 새로 부각되었고, 설정 오류(A02)가 상위로 올라왔다. 이 교안의 개념과 매핑하면 2-2는 A01·A07, 2-3은 A02·A04, 2-5는 A05, 2-7은 A09에 대응한다.

> **📌 핵심 정리** 위험 10개를 외우기보다 "내 서비스에서 어느 줄이 가장 아픈가"를 고르는 도구로 쓴다.

> **🗣 토론** 10개 중 AI가 만든 코드에서 가장 자주 빠질 것 같은 3개는? 이유를 가설로 적어 보자.

출처: OWASP Top 10:2025, top10.owasp.org/2025 (2026.11 확인).

## 2-9. 기본값이 곧 보안인가? (안전한 기본값)

**Q.** 설정을 안 건드리면 안전한가?

**A.** 안전해야 하지만, 현실에서는 "편한 기본값"이 사고로 이어진다. 안전한 기본값(Secure by Default)은 아무것도 설정하지 않았을 때 가장 닫혀 있는 상태를 말한다. 문을 일단 잠가 두고 필요한 곳만 여는 방식이다.

**Q.** 기본값이 사고를 낸 사례가 있는가?

> **⚠️ 실제 사례** 2025년 7월 여성 대상 데이트 안전 앱 Tea에서 접근 통제가 없던 예전 Firebase 저장소가 공개되어 7만 2천여 장의 이미지(신분증 사진 포함)가 유출되었고, 이후 약 110만 건의 DM 노출도 보도되었다. 회사는 이전 인프라의 잔여 저장소가 원인이라고 밝혔다. 교훈: 옛 저장소 폐기 점검, 기본 비공개, 민감 데이터 최소 수집이다. 수치는 보도마다 차이가 있어 가장 일관된 값만 적었다.

출처: Tea 공식 성명, Security Affairs·BleepingComputer 보도(2025.7).

**Q.** 바이브코딩에서는 어떻게 깨지는가?

**A.** AI는 "일단 돌아가게" 하려고 CORS 전체 허용, 디버그 모드 ON, 공개 버킷, RLS 끔 같은 느슨한 값을 고른다. 편한 설정이 그대로 출시된다.

> **📌 핵심 정리** 8개 개념을 한 줄로: 지킬 것을 정하고(CIA), 누구인지·해도 되는지 확인하고(인증/인가), 열쇠를 숨기고(비밀), 잠그고(암호화), 입력을 의심하고(인젝션), 필요한 만큼만 주고(최소권한), 기록하고(로깅), 닫힌 채 출발한다(기본값).

> **🛠 실습** 출시 직전 앱에서 "공개 상태인 것" 목록(버킷, API, 관리자 화면, 디버그 모드)을 만들어 보자.
