## 4-2. 의존성은 어떤 경로로 뚫리는가?

**Q.** 처음엔 "악성 패키지는 이름이 수상할 것"이라고 생각하기 쉽다. 맞는가?

**A.** 아니다. 공격자는 수상해 보이지 않는 경로를 고른다. 크게 세 갈래다.

| 경로 | 원리 | 예 |
|---|---|---|
| 이름 사칭 | 비슷한 이름으로 오설치 유도 | typosquatting |
| 계정·토큰 탈취 | 진짜 메인테이너 권한으로 새 버전 게시 | 게시 토큰 유출 |
| 설치 스크립트 | 설치 순간 임의 코드 실행 | preinstall/postinstall |

**Q.** 왜 "설치"만으로 위험한가?

**A.** npm은 설치 시 패키지가 선언한 스크립트를 실행할 수 있다. 앱을 켜기 전, 개발자 노트북이나 CI에서 코드가 돈다. 그곳에는 GitHub 토큰, 클라우드 키, `.env`가 있다.

**Q.** 직접 의존성만 보면 되는가?

**A.** 간접(전이) 의존성이 대부분이다. 프로젝트 하나에 수백 개가 딸려 올 수 있고, 어느 하나의 메인테이너 계정이 뚫리면 우리도 영향권이다.

> **🧪 가설**
> "유명하고 다운로드가 많은 패키지는 안전하다." 검증 방법: 이 파트의 사건 4건에서 피해 패키지의 인기도를 확인한다. 4-3, 4-4에서 반례를 본다.

> **💡 PM 시선**
> 공급망 사고는 "우리 코드의 버그"가 아니라 "구매한 부품의 결함"에 가깝다. 부품 목록(SBOM)과 입고 검수 규칙이 없으면 대응 시간이 길어진다. 지표 후보는 직접·간접 의존성 수, 마지막 갱신 후 경과일이다.

> **🚫 흔한 착각**
> "별(star)이 많으면 믿어도 된다." 별과 다운로드 수는 메인테이너 계정의 보안 수준을 보여주지 않는다.

## 4-3. Nx s1ngularity는 AI 도구를 어떻게 이용했나?

> **⚠️ 실제 사례**
> 2025년 8월 26일, 빌드 도구 Nx의 악성 버전이 npm에 게시되었다. 당시 주간 다운로드는 약 460만으로 보도되었다. 설치된 악성 코드는 개발자 PC의 Claude, Gemini, Amazon Q 같은 AI CLI를 권한 확인 생략 옵션으로 호출해 파일시스템에서 민감 정보를 찾게 했다. 탈취물은 피해자 계정에 자동 생성된 공개 GitHub 저장소로 올라갔다.

**Q.** 무슨 일이 가능했나?

**A.** 세 조각이 연결되었다. (1) 게시 토큰 탈취로 정상 패키지에 악성 버전 게시, (2) 설치 스크립트로 개발자 환경에서 실행, (3) 로컬에 설치된 AI CLI를 "도둑 비서"로 사용. 토큰 탈취 경위는 보고서마다 서술이 달라 여기서는 단정하지 않는다.

**Q.** 규모는?

**A.** GitGuardian은 저장소 1,346개와 시크릿 2,349건을 집계했고 대부분이 GitHub OAuth 키·개인 액세스 토큰이라고 보고했다.

> **🔍 탐구 과정**
> 처음 질문: "AI가 악성 코드를 시켰으면 AI 회사 책임 아닌가?" 확인: 일부 AI 클라이언트는 요청을 거부해 효과가 도구마다 달랐다고 보고되었다. 배운 점: 모델의 거부에만 기대면 안 되고, 에이전트를 사람 승인 없이 실행하는 옵션이 켜진 환경 자체가 공격 표면이다.

**Q.** 우리가 얻을 교훈은?

**A.** 개발 PC에 둔 장기 토큰의 위험, 에이전트 권한 우회 플래그 사용 습관, 설치 스크립트 실행 정책이 모두 점검 대상이다. 플래그의 설계는 Part 7에서 다룬다.

> **✅ 체크포인트**
> 내 PC에 `gh auth` 로그인과 AI CLI가 같이 있는가? 악성 설치 스크립트가 거기서 무엇을 읽을 수 있는지 설명할 수 있는가?

출처: Socket, Wiz 블로그(2025.8); GitGuardian 집계 인용(보도 기준)

## 4-4. 웜과 CI 도구 오염은 어떻게 이어졌나?

**Q.** s1ngularity 이후 무엇이 달라졌나?

**A.** 공격이 "한 번"에서 "자기 복제"와 "방어 도구 오염"으로 번졌다. 사건 연표는 아래와 같다(규모 수치는 출처마다 달라 대략으로 표기).

| 시기 | 사건 | 요점 |
|---|---|---|
| 2025.9 | Shai-Hulud | 탈취 npm 토큰으로 피해자의 다른 패키지에 악성 버전을 게시하는 웜. 수백 개 패키지 |
| 2025.11 | Shai-Hulud 2.0 | preinstall로 실행, 공개 GitHub 저장소로 유출. 수백 개 패키지 |
| 2026.3 | Trivy 오염 | 보안 스캐너 Action의 버전 태그가 악성 커밋을 가리키도록 재지정 |
| 2026.3 | LiteLLM | 유출된 자격증명으로 PyPI에 악성 릴리스 2건 |
| 2026.5 | Mini Shai-Hulud | TanStack, Mistral AI SDK 등 npm 170여 개와 PyPI 2개 |

> **⚠️ 실제 사례**
> 2026년 3월 19일, 보안 스캐너 `trivy-action`의 대부분 버전 태그(75~76개로 보도, 매체별 차이)가 악성 커밋을 가리키도록 바뀌었다. 같은 달 24~25일(매체별 차이) LiteLLM의 PyPI 악성 릴리스 1.82.7, 1.82.8이 게시됐고, LiteLLM CI가 Trivy를 버전 고정 없이 실행하다 게시 토큰이 유출된 것으로 보도되었다.

**Q.** 반복되는 공통점은?

**A.** 목표는 코드가 아니라 **자격증명**이다. 탈취한 토큰이 다음 패키지를 감염시키는 연료가 된다.

> **🧪 가설**
> "보안 도구를 쓰면 공급망 공격에서 안전하다." 반증: 보안 스캐너 자체가 오염 대상이었다. 도구도 의존성이므로 고정·검증 대상이다.

> **🗣 토론**
> 우리 팀의 CI가 쓰는 외부 Action·패키지 중 "침해되면 가장 아픈 3개"는? 그 3개에 어떤 시크릿이 노출되는가?

## 4-5. lockfile·고정·쿨다운은 무엇을 막나?

**Q.** `^1.2.3` 같은 범위 표기가 왜 위험한가?

**A.** 설치 시점에 "가장 새로운 호환 버전"이 선택된다. 방금 게시된 악성 버전이 곧바로 들어올 수 있다. lockfile(`package-lock.json`, `pnpm-lock.yaml`, `uv.lock` 등)은 검증한 버전과 해시를 기록해 이를 막는다.

**Q.** CI에서 무엇을 쓰나?

**A.** lockfile 그대로만 설치하는 명령이다.

```
# npm: lockfile과 다르면 실패, 새 버전 임의 선택 없음
npm ci --ignore-scripts

# Python (uv): lockfile 기준 설치
uv sync --frozen
```

**Q.** "쿨다운(최소 릴리스 연령)"은 무엇인가?

**A.** 게시된 지 N일이 안 된 버전은 설치하지 않는 정책이다. 악성 버전은 보통 발견·삭제까지 시간이 짧아, 며칠만 기다려도 피해를 줄인다. 도구별로 이미 지원된다.

| 도구 | 설정 | 단위 |
|---|---|---|
| npm 11.10+ | `min-release-age` | 일 |
| pnpm | `minimumReleaseAge` | 분 |
| uv | `exclude-newer` | 기간/날짜 |

단위가 다르므로 복사해 쓰지 말고 문서로 확인한다. 기본값도 버전마다 다를 수 있다(확인 필요).

> **💡 PM 시선**
> 쿨다운의 비용은 "신규 버전을 며칠 늦게 쓰는 것"뿐이다. 보안 패치는 예외 규칙을 둔다. 속도와 보안의 트레이드오프를 숫자로 협의하기 좋은 항목이다.

> **🧪 가설**
> "쿨다운 7일이면 대부분의 신규 악성 버전을 피한다." 검증: 최근 사건의 게시~삭제 간격을 사건별로 조사해 비교한다. 이 간격 데이터는 팀이 직접 모아야 한다.

**npm 토큰 정책:** 2025년 11월 신규 classic 토큰 생성이 중단되었고, 12월 9일 기존 classic 토큰이 모두 폐기되었다. 게시용 granular 토큰은 최대 90일이다.

## 4-6. SCA·SBOM 도구는 무엇을 고르나?

**Q.** SCA와 SBOM은 무엇인가?

**A.** SCA(Software Composition Analysis)는 쓰는 부품의 알려진 취약점·라이선스를 찾는 일이고, SBOM은 부품 목록 자체다. 사고가 나면 "우리가 그 버전을 쓰는가?"에 몇 분 안에 답하는 것이 목표다.

**Q.** 도구는 어떻게 비교하나?

**A.** 경쟁·대안 관점으로, 질문은 "무엇을 탐지하나"다.

| 도구 | 강점 | 한계 |
|---|---|---|
| Dependabot | GitHub 내장, 알려진 취약점 알림·업데이트 PR | 신규 악성 패키지 탐지에는 약함 |
| Renovate | 업데이트 자동화, 쿨다운 설정 가능 | 설정 학습 필요 |
| Snyk | 상용, 우선순위·수정 제안 | 비용, 알려진 취약점 중심 |
| Socket | 설치 스크립트·네트워크 접근 등 행위 신호 | 신호 해석과 오탐 조정 |
| OSV-Scanner | 오픈소스, lockfile 스캔, OSV DB | 업데이트 자동화는 별도 |
| npm audit | 기본 내장, 무료 | 알려진 취약점만 |

**Q.** 하나만 고른다면?

**A.** 취약점 DB 기반 도구는 "이미 알려진 것"에, 행위 분석 도구는 "새 악성"에 강하다. 둘은 경쟁이 아니라 보완이다. 1인 빌더라면 Dependabot과 `npm ci`·쿨다운으로 시작하고, 위험이 커지면 행위 분석을 얹는다.

> **🔍 탐구 과정**
> 처음 가정: "알려진 취약점 DB로 충분하다." 확인: Part 4-3, 4-4의 사건은 사건 당시 취약점 DB에 없는 "새 악성 버전"이었다. 배운 점: 알림 기반 도구만으로는 첫 몇 시간을 못 막는다.

> **🛠 실습**
> 내 프로젝트에 `osv-scanner -r .`(또는 `npm audit`)을 돌려 결과를 받는다. 심각도가 높은 항목 하나를 골라 "직접 쓰는가? 고쳐진 버전이 있는가?"를 판정한다.

## 4-7. AI가 지어낸 패키지와 에이전트 설치는?

**Q.** AI가 존재하지 않는 패키지를 추천하면 무슨 문제인가?

**A.** 공격자가 그 이름으로 악성 패키지를 먼저 등록해 두면, AI 추천을 믿고 설치한 사람이 감염된다. 이를 slopsquatting(환각 패키지 선점)이라 부른다. Part 3에서 원리를 다뤘으므로 여기서는 방어 규칙만 정리한다.

**Q.** 코딩 에이전트가 직접 `npm install`을 한다면?

**A.** 사람의 눈이 사라진 만큼 가드가 필요하다. 에이전트의 설치 행위를 "코드 실행 권한 부여"로 본다.

| 가드 | 내용 |
|---|---|
| 승인 | 새 의존성 추가는 사람 승인 필수 |
| 사전 조회 | 레지스트리 등록일·다운로드·저장소 링크 확인 |
| 스크립트 차단 | `--ignore-scripts`, 필요한 것만 허용 |
| 격리 | 설치·실행은 키 없는 샌드박스에서 |
| 기록 | lockfile 변경을 PR로 리뷰 |

**Q.** 체크 항목을 구체적으로 보면?

**A.** 새 패키지 하나당 1분 안에 확인한다.
- 이름 철자가 의도한 패키지와 같은가
- 최초 게시일이 며칠 전은 아닌가
- 저장소 링크와 메인테이너가 실재하는가
- 같은 기능을 표준 라이브러리로 쓸 수 없는가

> **⚠️ 실제 사례**
> 2025년 8월 Nx 사건에서 악성 코드는 개발자 PC의 AI CLI가 승인 없이 돌아가는 옵션을 이용했다. 에이전트의 "자동 승인" 모드와 설치 스크립트가 만나는 지점이 위험하다는 교훈이다.

> **🧪 가설**
> "에이전트에게 설치 권한을 주면 속도가 크게 오른다." 검증: 새 의존성 추가 PR의 리뷰 소요 시간과 사고 건수를 한 달 동안 비교한다.

> **🛠 실습**
> 프로젝트의 에이전트 지침 파일에 "새 의존성은 이름·등록일·저장소를 보고한 뒤 승인받아 추가한다" 한 줄을 넣고, 에이전트가 실제로 지키는지 테스트한다.

## 4-8. GitHub Actions는 어떻게 지키나?

**Q.** CI/CD가 왜 공격 1순위가 되었나?

**A.** CI에는 배포 키, 게시 토큰, 클라우드 자격증명이 모여 있고 사람의 눈이 닿지 않는다. 4-4의 Trivy 사건도 CI 도구를 겨냥했다.

**Q.** 가장 먼저 할 일은?

**A.** 네 가지다.
1. **권한 최소화**: 기본 `GITHUB_TOKEN`을 읽기 전용으로 낮춘다.
2. **핀 고정**: 서드파티 Action을 태그가 아닌 전체 커밋 SHA로 고정한다. 태그는 다른 커밋을 가리키도록 바뀔 수 있다.
3. **위험 트리거 경계**: `pull_request_target`은 외부 PR에서도 시크릿을 가진 채 돈다. 외부 코드를 체크아웃해 실행하면 위험하다.
4. **PR 입력을 셸에 직접 삽입 금지**: 제목·브랜치명은 공격자가 쓴 글이다.

```
permissions:
  contents: read          # 기본은 읽기만
steps:
  - uses: actions/checkout@<전체-커밋-SHA>   # 태그 대신 SHA
    with:
      persist-credentials: false
```

**Q.** GitHub는 무엇을 바꾸고 있나?

**A.** 2026년 3월 GitHub는 Actions 보안 로드맵을 공개했다. 핵심은 워크플로 의존성 잠금(lockfile 유사)과 실행 환경 통제다. `pull_request_target` 기본 차단 시행일은 보도마다 달라(11월 또는 12월) 확인이 필요하다. 출시 여부는 GitHub 공식 changelog로 확인한다.

> **🚫 흔한 착각**
> "SHA로 핀하면 끝이다." 복합 액션 내부가 다시 부르는 하위 의존성은 SHA 핀으로 못 잡는다는 지적이 있다.

> **🛠 실습**
> 내 저장소 `.github/workflows`에서 `uses:` 줄을 모두 찾는다(`grep -rn "uses:" .github`). 태그(`@v4`)로 된 것을 세고, 가장 중요한 하나를 SHA로 바꿔 본다.

## 4-9. 시크릿은 어떻게 관리하고 유출 시 어떻게 대응하나?

**Q.** 처음엔 "키를 안전한 곳에 숨기면 된다"고 생각하기 쉽다. 충분한가?

**A.** 숨기는 것만으로는 부족하다. 목표는 **유출돼도 피해가 작게** 만드는 것이다. 장기 토큰 대신 단기 토큰, 사람이 쥔 키 대신 워크로드 신원이 핵심이다.

| 방식 | 위험 | 대안 |
|---|---|---|
| 코드·`.env` 커밋 | 영구 노출 | 시크릿 매니저, 스캔 |
| 장기 클라우드 키 | 탈취 후 오래 유효 | OIDC로 단기 자격 |
| 만료 없는 게시 토큰 | 웜의 연료 | 신뢰 게시(Trusted Publishing) |
| 모든 환경 공용 키 | 피해 범위 확대 | 환경별 분리·최소권한 |

**Q.** 신뢰 게시란?

**A.** CI가 OIDC로 "이 저장소의 이 워크플로가 게시한다"를 증명해 단기 자격을 받는 방식이다. npm은 GitHub Actions와 GitLab CI/CD를 지원하며, 토큰을 저장소에 둘 필요가 없다. 출처 증명(provenance)을 붙이면 "어느 소스에서 빌드됐나"를 소비자가 검증할 수 있다.

> **⚠️ 실제 사례**
> 4-3의 s1ngularity는 개발자 환경의 GitHub 토큰을 대량 탈취했고, Shai-Hulud는 탈취한 게시 토큰으로 확산했다. 둘 다 "오래 쓰는 토큰"이 핵심 연료였다.

**Q.** 유출됐다면 첫 1시간은?

**A.** 순서가 중요하다.
1. **폐기·교체**: 키를 즉시 revoke하고 새로 발급(삭제보다 폐기가 먼저)
2. **범위 확인**: 로그에서 그 키로 한 행동 조회
3. **격리**: 감염 의심 기기·러너 분리, 재구축
4. **이력 정리**: 커밋에서 제거하되 "이미 유출"로 간주
5. **기록**: 타임라인을 남겨 포스트모템

> **🛠 실습**
> 테스트용 가짜 키를 임시 저장소에 커밋하고 `gitleaks`로 탐지한 뒤, 위 5단계를 순서대로 표로 적는다.

## 4-10. 정리와 실습

> **📌 핵심 정리**
> - 위험 경로는 이름 사칭, 계정·토큰 탈취, 설치 스크립트다. 인기도는 안전 보증이 아니다.
> - 최근 사건의 공통 연료는 **장기 자격증명**이다. 단기 토큰·OIDC·신뢰 게시로 줄인다.
> - lockfile + `npm ci` + 쿨다운 + 스크립트 제한이 비용 대비 효과가 크다.
> - 보안 도구와 CI Action도 의존성이다. 전체 SHA로 고정하고 권한을 줄인다.
> - 에이전트의 의존성 설치는 "코드 실행 권한 부여"로 취급해 승인·격리한다.

**Q.** 이번 파트의 가설들은 어디까지 검증됐나?

**A.** "인기 패키지는 안전" 가설은 사건으로 반증됐다. "쿨다운 7일이면 충분"은 팀의 데이터로 검증이 필요하다.

| 우선순위 | 오늘 할 일 | 시간 |
|---|---|---|
| 1 | CI에서 `npm ci`, `GITHUB_TOKEN` 읽기 전용 | 30분 |
| 2 | 쿨다운 설정과 Dependabot 켜기 | 30분 |
| 3 | 외부 Action SHA 핀 | 1시간 |
| 4 | 장기 키 목록 작성, OIDC 전환 계획 | 반나절 |

> **🛠 실습**
> 내 서비스의 "토큰·키 인벤토리"를 표로 만든다. 열은 이름, 위치, 권한 범위, 만료일, 유출 시 피해 범위로 한다. 만료일이 없는 항목 3개에 교체 일정을 정한다.

> **🗣 토론**
> 쿨다운(신규 버전 지연)과 즉시 패치 적용은 충돌한다. 보안 패치는 예외로 둘지, 누가 승인할지, 어떤 지표(MTTR 등)로 판단할지 팀 규칙을 정해 본다.

> **💡 PM 시선**
> 공급망 보안은 고객에게 "키·데이터 유출이 없었다"는 신뢰로 돌아온다. 보안 질문서와 엔터프라이즈 영업에서 SBOM·핀 고정·시크릿 정책은 점점 증빙 대상이 된다.
