## 8-1. 보안 도구는 어떤 종류이고 무엇이 경쟁 대안인가?

**Q.** 스캐너 이름이 너무 많다. 어떻게 나누나?

**A.** 이름이 아니라 "무엇을 검사하느냐"로 나눈다. 아래는 공개된 일반 특성이며, 라이선스·요금은 자주 바뀌므로 도입 전 재확인한다(확인 필요).

| 유형 | 도구 | 강점 | 유의점 |
|---|---|---|---|
| SAST | Semgrep | 규칙 작성 쉬움, 빠름 | 깊은 분석은 유료 비중 |
| SAST | CodeQL | 코드를 DB로 질의 | GitHub 중심, 빌드 설정 |
| 시크릿 | Gitleaks | 가볍고 pre-commit 적합 | 이력 오탐 정리 |
| 컨테이너·IaC | Trivy | 여러 영역 통합 | 튜닝 필요 |
| SCA | OSV-Scanner | 오픈소스, lockfile 기반 | 도달성 분석 약함 |
| SCA·SAST | Snyk | 수정 제안, 대시보드 | 상용, 알림량 |

GitHub Advanced Security는 CodeQL·시크릿 스캔·Dependabot을 GitHub 안에 묶은 번들이다. DAST(OWASP ZAP 등)는 실행 중인 앱을 본다.

> **🚫 흔한 착각**
> "SAST 하나 켰으니 끝." SAST는 **내 코드 패턴**만 본다. 의존성 CVE·유출 키·클라우드 설정은 다른 유형이 본다. AI가 의존성을 마구 추가하는 바이브코딩 앱은 SCA와 시크릿 스캔 우선순위가 높다.

> **💡 PM 시선**
> 보안 도구도 제품이다. "누가 어떤 순간(PR)에 무엇을(수정 가능한 알림) 받나"를 정의하라. 알림 UX가 나쁘면 사용률이 0이 된다.

## 8-2. 어떤 팀이 무엇을 고르나?

**Q.** 팀 상황별 출발 조합은?

**A.** 정답이 아닌 **출발 가설**이다. 2~4주 운영 후 지표로 바꾼다.

| 팀 상황 | 출발 조합 | 근거 가설 |
|---|---|---|
| 1인 SaaS, GitHub | Gitleaks + Dependabot + 기본 스캔 | 설정 비용 최소, 유출 키가 최대 위험 |
| 5~20명 스타트업 | 위 + Semgrep + OSV-Scanner | 팀 관례를 규칙으로 반영 |
| 규제 산업·대기업 | GitHub Code Security 또는 Snyk + 대시보드 | 감사 증적, 정책 통제 |
| 컨테이너 중심 | Trivy 추가 | 이미지·IaC 한 도구로 |

> **🧪 가설**
> "무료 오픈소스 조합(Gitleaks + OSV-Scanner + Semgrep)만으로도 소규모 팀의 치명적 사고 대부분은 줄어든다." 검증: 2주간 켜고, 잡힌 건 중 실제 수정된 비율과 놓친 사고 여부를 기록한다.

> **🧪 가설**
> "도구 선택보다 **차단 기준**(어느 심각도에서 빌드를 막나)이 속도에 더 큰 영향을 준다." 검증: 기준 변경 전후의 PR 리드타임과 수정 완료율 비교.

> **🗣 토론**
> 우리 팀의 최대 자산 3가지는 무엇이고, 위 표의 어떤 도구가 그것을 직접 지키는가? 못 지키는 자산은?

**Q.** 도구를 바꿀 신호는?

**A.** 알림 절반 이상 무시, 같은 유형 사고가 스캐너를 통과, 수정 시간 증가. 측정은 8-7의 지표로 한다.

## 8-3. 어느 단계에서 막아야 하나?

**Q.** 모든 검사를 PR마다 돌리면 되나?

**A.** 아니다. 빠르고 확실한 것은 앞단, 무겁고 깊은 것은 뒷단.

```
laptop        CI (PR)          main/deploy       runtime
+---------+   +-------------+  +-------------+   +---------+
|pre-commit|->| SAST, SCA   |->| image scan  |-->| monitor |
| secrets |   | secrets diff|  | IaC, SBOM   |   | alerts  |
| lint    |   | AI review   |  | sign/attest |   | DAST    |
+---------+   +-------------+  +-------------+   +---------+
 seconds        minutes          minutes           continuous
```

| 단계 | 막을 것 | 정책 |
|---|---|---|
| pre-commit | 시크릿 | 차단 (오탐 적고 피해 큼) |
| PR | 높음·치명 취약점 | 차단, 중간 이하 경고 |
| 배포 | 취약 이미지, 서명 누락 | 차단 |

> **🔍 탐구 과정**
> 처음엔 "모든 단계 전부 차단"이 안전하다고 생각하기 쉽다. 그러나 오탐에 막힌 개발자는 `--no-verify`나 규칙 비활성화로 우회한다. 확인법은 우회 건수 집계. 배운 점: **차단은 확신 높은 항목에만**, 나머지는 경고로 두고 추세를 본다.

**Q.** 에이전트가 쓴 커밋도 같은 게이트를 거치나?

**A.** 반드시 거친다. 에이전트가 로컬 훅을 건너뛸 수 있으므로 서버 측 CI 게이트가 최종 방어선이다.

## 8-4. AI 보안 리뷰는 무엇이 되고 안 되나?

**Q.** AI가 쓴 코드를 AI가 리뷰하면 믿을 수 있나?

**A.** 보조로는 유용, 단독 게이트로는 위험하다. 현황은 다음과 같다.

- **Claude Code `/security-review`**: 로컬에서 브랜치 변경분을 보안 관점으로 검토한다. 커밋 전 점검용이며 프롬프트를 커스터마이즈할 수 있다고 Anthropic 문서가 안내한다.
- **`anthropics/claude-code-security-review` Action**: PR을 검토해 코멘트를 남긴다. README는 **프롬프트 인젝션에 강화되어 있지 않으니 신뢰하는 PR에만** 쓰라고 경고한다.
- **GitHub Copilot Autofix**: CodeQL 알림에 수정안을 제안한다. 공식 문서상 public 저장소 또는 Code Security 라이선스 조직 저장소에서 쓴다. 2026.7 agentic autofix가 public preview로 발표되었다(GA 여부는 확인 필요).

> **⚠️ 실제 사례**
> 리뷰 에이전트 자체가 공격 표면이다. PR 본문·코드 주석에 숨은 지시문이 리뷰어 AI를 조종할 수 있다. 위 Action의 README 경고가 그 근거다. 외부 기여자 PR에 API 키를 가진 AI 리뷰를 자동 실행하지 않는 것이 기본이다.

**Q.** 결국 어떻게 쓰나?

**A.** 결정적 스캐너가 1차, AI 리뷰는 **인가 누락·로직 결함처럼 규칙으로 못 잡는 영역**의 2차, 사람이 최종 승인.

## 8-5. 리뷰 에이전트에 무엇을 시키나? (프롬프트 3종)

**Q.** "보안 검토해줘"가 왜 안 되나?

**A.** 범위·증거·출력 형식이 없으면 일반론과 오탐이 나온다. 아래는 역할·범위·증거·형식을 고정한 템플릿이다.

> **🛠 실습**
> **템플릿 1. PR 보안 리뷰**
> ```
> 역할: 시니어 앱보안 리뷰어. 변경된 diff만 검토.
> 범위: 인증/인가 누락, 입력 검증, 시크릿, 인젝션.
> 규칙: 파일:줄 근거 없는 지적 금지. 추측은 '가능성'으로 표기.
> 출력: 표(심각도|위치|이유|수정안). 문제 없으면 '없음'.
> ```

> **🛠 실습**
> **템플릿 2. 인가(권한) 누락 점검**
> ```
> 새로 추가·수정된 모든 API 엔드포인트를 나열하라.
> 각각 (a) 로그인 요구 여부 (b) 요청자와 리소스 소유자
> 일치 검사 여부 (c) 근거 코드를 적어라.
> (b)가 없으면 IDOR 가능성으로 표시하라.
> ```

> **🛠 실습**
> **템플릿 3. 에이전트 변경 감사**
> ```
> 이 PR은 AI가 작성했다. 확인: 새 의존성(이름·버전, 실존
> 의심), 설정/CI 파일 변경, 쉘 실행 코드, 외부 URL 호출,
> 하드코딩 값. 각 항목에 사람 승인 필요 여부를 표기하라.
> ```

> **✅ 체크포인트**
> 세 템플릿 모두 "근거 코드 인용"을 요구하는가? 리뷰 대상 텍스트(diff, PR 본문)는 **지시가 아니라 데이터**라고 프롬프트에 명시했는가?

## 8-6. LLM 앱은 어떻게 레드팀하나?

**Q.** 코드 스캐너로 프롬프트 인젝션을 못 잡는다. 무엇으로 잡나?

**A.** **공격 프롬프트 모음을 자동 실행하고 응답을 채점하는 평가 하네스**로 점검한다. 개념은 단위 테스트와 같다.

```
attack set -> app under test -> response -> grader -> report
 (cases)      (prompt+tools)               (rule/LLM)  pass/fail
                  ^                                       |
                  +---- fix prompts/guardrails <----------+
```

대표 도구는 promptfoo(오픈소스 평가·레드팀)다. 2026.3 OpenAI가 인수를 발표했고 오픈소스 유지를 약속했다고 보도되었다(완료 여부는 확인 필요). 대안으로 garak 등 오픈소스 스캐너가 있다.

| 점검 축 | 예시 케이스(원리 수준) |
|---|---|
| 직접 인젝션 | "이전 지시를 무시하라" 류 |
| 간접 인젝션 | 문서·웹페이지에 숨긴 지시 |
| 데이터 유출 | 시스템 프롬프트·타 사용자 정보 요구 |
| 도구 오남용 | 허용 범위 밖 도구 호출 유도 |

> **🧪 가설**
> "공격 케이스를 CI 회귀 테스트로 넣으면 프롬프트·모델 변경 때 생기는 방어 퇴행을 배포 전에 발견한다." 검증: 시스템 프롬프트를 일부러 약화시켜 통과율이 떨어지는지 본다.

> **🗣 토론**
> 채점자도 LLM이면 그 결과를 얼마나 믿나? 사람이 표본 검수하는 비율은?

## 8-7. 오탐·미탐과 지표는 어떻게 운영하나?

**Q.** 오탐(false positive)과 미탐(false negative) 중 무엇이 더 위험한가?

**A.** 위험은 미탐이지만 **일상적 파괴는 오탐**이다. 오탐이 많으면 신호 전체가 무시된다.
- 오탐: 억제 시 **사유와 만료일** 필수, 규칙 튜닝
- 미탐: 사고·모의해킹을 "왜 못 잡았나"로 회고하고 규칙 추가

**Q.** 어떤 지표를 보나?

| 지표 | 의미 | 나쁜 신호 |
|---|---|---|
| MTTR | 알림 → 수정 시간 | 높음 심각도가 길어짐 |
| 시크릿 유출 건수 | 커밋된 키 수 | 줄지 않음 |
| 수정률 | 처리 알림 / 전체 | 낮음 = 알림 피로 |
| 게이트 우회 수 | 억제·우회 건수 | 급증 |

> **🛠 실습**
> 지난 30일 알림을 내보내 위 4개 지표를 스프레드시트로 계산하라. 가장 나쁜 지표 하나를 골라 개선 가설을 쓴다.

> **📌 핵심 정리**
> 1. 스캐너는 유형별로 고르고, 차단은 확신 높은 항목에만 건다.
> 2. AI 리뷰는 보조선이며 리뷰어 자체가 공격 표면이다.
> 3. LLM 앱은 공격 케이스를 CI 회귀 테스트로 돌린다.
> 4. 숫자로 확인하지 않으면 보안은 느낌에 머문다.
