## 3-1. 연구는 AI 코드 보안에 대해 무엇을 말하는가?

**Q.** "AI 코드의 절반은 취약하다"는 말을 믿어도 되는가?

**A.** 절반쯤 맞고 절반쯤 과장이다. 출처부터 확인해야 한다.

> **⚠️ 실제 사례** Veracode의 2025 GenAI Code Security Report는 100개 이상의 LLM에 CWE 기반 코딩 과제 80개를 풀게 했다. 보도자료 기준으로 AI 코드가 보안 취약점을 만든 비율은 45%였다. 언어별로는 Java의 실패율이 70%를 넘었고, Python·C#·JavaScript는 38~45% 범위였다. 입력 문맥에 의존하는 XSS는 안전한 코드가 12~13%에 그쳤다는 보도가 있다.

**Q.** 이 수치를 어떻게 읽어야 하나?

**A.** 세 가지를 지킨다.
- 모집단: "큐레이션된 과제 세트에서의 비율"이다. 세상 모든 AI 코드의 비율이 아니다.
- 비교군: 사람 코드의 같은 지표와 나란히 놓인 수치가 아니다.
- 추세: 모델이 커져도 보안 점수는 크게 오르지 않았다는 것이 보고서의 메시지다. 후속 업데이트의 모델별 수치는 원문 확인이 필요하다.

> **🧪 가설** "AI는 문법·기능은 잘 맞히지만, 맥락이 필요한 보안 판단(누가 접근하나, 입력은 어디서 오나)은 프롬프트에 적히지 않으면 건너뛴다."

**Q.** 그래서 PM은 무엇을 해야 하나?

**A.** 통계로 AI 도입 여부를 논쟁하기보다, 우리 저장소에서 자체 측정한다. 예를 들어 "AI가 작성한 PR의 스캐너 경고 수 / 사람 PR의 경고 수"를 한 달만 비교해도 가설을 검증할 수 있다.

출처: Veracode, 「2025 GenAI Code Security Report」 및 보도자료(2025.7), veracode.com. 세부 수치는 보도 요약 기준이므로 인용 전 원문 확인.

## 3-2. 반복되는 취약 패턴은 무엇인가?

**Q.** 바이브코딩 결과물에서 자주 보이는 패턴을 한 장으로 정리하면?

**A.** 아래 7가지가 대부분이다. 각 개념의 정의는 Part 2를 참고한다.

| 패턴 | AI 코드에서의 모습 | 위험 |
|---|---|---|
| 하드코딩 시크릿 | 예제 따라 `API_KEY = "sk-..."`를 코드에 직접 기재 | 저장소 유출 시 즉시 도용 |
| SQL 문자열 결합 | f-string·템플릿 리터럴로 쿼리 조립 | SQL 인젝션 |
| 인가 누락 | 로그인만 확인하고 "내 데이터인가"는 확인 안 함 | 남의 데이터 열람(IDOR) |
| 약한 인증·세션 | 평문·단순 해시 비밀번호, 만료 없는 토큰 | 계정 탈취 |
| 과도한 CORS | `origin: "*"` 또는 요청 Origin 그대로 반사 | 타 사이트의 API 호출 |
| 검증 누락 | 입력 타입·길이·형식을 믿고 사용 | 인젝션, 서비스 오류 |
| 에러·설정 노출 | 스택트레이스 응답, 디버그 모드 배포 | 내부 구조 노출 |

> **🔍 탐구 과정** 처음엔 "AI가 일부러 허술하게 쓴다"고 생각하기 쉽다. 하지만 이 패턴들은 튜토리얼과 예제에 흔한 "일단 돌아가는 코드"와 같다. 학습 데이터에 많은 형태를 재생산한다고 보면, 문제는 악의가 아니라 기본값이 개발 환경 기준이라는 점이다. 확인 방법: 같은 기능을 "보안 요구사항 없이" 3번 생성해 위 표로 채점해 본다.

**Q.** 표에서 가장 먼저 볼 곳은?

**A.** 데이터가 드나드는 경계(DB 쿼리, 라우트 핸들러, 설정 파일)다. 이 세 곳이 다음 세 쪽의 주제다.

## 3-3. SQL 문자열 결합은 어떻게 고치나? (비교 1)

**Q.** 검색 기능을 AI에게 시키면 어떤 코드가 나오기 쉬운가?

**A.** 아래처럼 입력값을 쿼리에 직접 붙이는 코드가 흔하다. (Python, 방어 목적의 최소 예시)

```python
# 취약: 입력이 쿼리 문법의 일부가 된다
def find_user(conn, name):
    q = f"SELECT id, email FROM users WHERE name = '{name}'"
    return conn.execute(q).fetchall()

# 수정: 값은 파라미터로 분리한다
def find_user(conn, name):
    q = "SELECT id, email FROM users WHERE name = ?"
    return conn.execute(q, (name,)).fetchall()
```

**Q.** 왜 위쪽이 위험한가?

**A.** 입력이 "데이터"가 아니라 "명령의 일부"로 해석되기 때문이다. 수정본은 쿼리 구조를 먼저 고정하고 값을 따로 전달하므로 입력이 명령으로 바뀔 수 없다. 이는 Part 5에서 볼 프롬프트 인젝션의 뿌리(지시와 데이터의 혼합)와 같은 구조다.

> **🚫 흔한 착각** "따옴표를 치환(escape)하면 된다." 직접 만든 치환 함수는 빠뜨리는 경우가 생긴다. 검증된 파라미터 바인딩이나 ORM의 쿼리 빌더를 쓴다. ORM에서도 raw 쿼리에 문자열을 붙이면 같은 문제가 재발한다.

**Q.** 리뷰에서 어떻게 잡나?

**A.** 검색어 `f"SELECT`, `"SELECT " +`, `` `SELECT ${ `` 를 저장소 전체에서 찾는다. 이 검색은 1분이면 끝나고, Semgrep 같은 SAST 도구(Part 8)가 자동으로 해 주는 일이기도 하다.

> **💡 PM 시선** 이 버그는 화면에서 보이지 않는다. 기능 테스트가 통과해도 안전하다는 증거가 아니라는 점을 팀과 합의해 두자.

## 3-4. 남의 데이터가 보이는 버그는? (비교 2)

**Q.** 로그인 기능이 있는데 왜 남의 주문이 보이나?

**A.** 인증(누구인가)과 인가(무엇을 할 수 있나)를 혼동했기 때문이다. AI는 "로그인 필요" 미들웨어는 잘 붙이지만, 객체 소유자 확인은 자주 빠뜨린다. (TypeScript/Express 예시)

```typescript
// 취약: 로그인만 확인하고 id로 바로 조회한다
app.get("/orders/:id", requireLogin, async (req, res) => {
  const order = await db.order.findUnique({ where: { id: req.params.id } });
  res.json(order);
});

// 수정: 조회 조건에 "내 것"을 포함한다
app.get("/orders/:id", requireLogin, async (req, res) => {
  const order = await db.order.findFirst({
    where: { id: req.params.id, userId: req.user.id },
  });
  if (!order) return res.sendStatus(404);
  res.json(order);
});
```

**Q.** 수정본의 포인트는?

**A.** 두 가지다. 소유자 조건을 쿼리에 넣어 "남의 것"을 애초에 못 읽게 했고, 없을 때와 남의 것일 때 모두 404로 답해 존재 여부도 알리지 않는다.

> **🧪 가설** "ID가 순번이어도 인가가 있으면 안전하고, UUID여도 인가가 없으면 위험하다." 검증: 테스트 계정 두 개로 A의 URL을 B 로그인 상태에서 열어 본다. 이 한 번의 수동 테스트가 많은 정적 분석보다 빠를 때가 있다.

> **💡 PM 시선** 인가 규칙은 코드가 아니라 제품 규칙이다. "누가 무엇을 볼 수 있나"를 표로 먼저 정의해 AI에게 주면 누락이 줄어든다(3-8쪽).

## 3-5. CORS와 에러 노출은? (비교 3)

**Q.** 프론트에서 API 호출이 막힐 때 AI가 가장 흔히 내놓는 해법은?

**A.** "CORS를 전부 열어라"이다. 개발 중 막힘은 사라지지만 배포 설정에 그대로 남는다. (TypeScript/Express)

```typescript
// 취약: 모든 출처 허용 + 내부 오류를 그대로 응답
app.use(cors({ origin: "*", credentials: true }));
app.use((err, req, res, next) => {
  res.status(500).json({ message: err.message, stack: err.stack });
});

// 수정: 허용 출처를 명시하고, 오류는 일반 문구만 응답
const allowed = ["https://app.example.com"];
app.use(cors({ origin: allowed, credentials: true }));
app.use((err, req, res, next) => {
  logger.error({ err, path: req.path }); // 상세는 서버 로그에만
  res.status(500).json({ message: "서버 오류가 발생했다." });
});
```

**Q.** 무엇이 개선됐나?

**A.** 첫째, 쿠키·토큰이 실린 요청을 신뢰한 출처에서만 허용한다. 둘째, 스택트레이스와 경로 같은 내부 정보는 사용자가 아닌 로그로 보낸다.

> **🚫 흔한 착각** "프런트가 막으면 안전하다." CORS는 브라우저가 지키는 규칙이다. 서버 간 호출이나 직접 요청에는 효과가 없으므로 인가 검사를 대신하지 못한다.

**Q.** 환경 차이는 어떻게 관리하나?

**A.** 허용 출처를 환경 변수로 분리하고, 운영 환경에서 `*`가 있으면 배포가 실패하도록 CI에 검사를 넣는다. 디버그 모드와 샘플 계정도 같은 방식으로 점검한다.

> **🛠 실습** 내 프로젝트에서 `origin: "*"`, `DEBUG`, `err.stack`을 검색하고 결과를 3줄로 기록하라.

## 3-6. BaaS 설정 실수는 왜 치명적인가?

**Q.** Supabase·Firebase를 쓰면 서버 코드가 없는데 보안은 누가 책임지나?

**A.** 서버가 없을 뿐 규칙은 있다. 브라우저가 DB에 직접 접근하므로, 접근 제어는 DB의 정책(Supabase RLS, Firebase Security Rules)이 전부 맡는다. 정책이 비면 공개 키만으로 읽고 쓸 수 있다.

> **⚠️ 실제 사례** CVE-2025-48757은 Lovable이 생성한 프로젝트에서 RLS 정책이 부족해 인증 없는 사용자가 테이블을 읽거나 쓸 수 있었다는 취약점으로 등록됐다. 연구자 Matt Palmer의 스캔에서는 공개 쇼케이스 앱 1,645개 중 170개(약 10%)에서 노출이 확인됐다고 알려졌다. CVE 레코드(2025.5.30 공개, CVSS 9.3)에는 "공급사는 각 고객이 자기 앱 데이터 보호에 책임이 있다며 이의를 제기"한다는 단서가 붙어 있다. 교훈은 설정 책임이 어디에 있든 출시 전 검증이 필요하다는 점이다.

**Q.** 최소한의 방어 설정은?

```sql
-- 테이블마다 RLS를 켠다 (켜고 정책이 없으면 모두 거부)
alter table orders enable row level security;

-- 내 행만 읽기
create policy "own_orders_select" on orders
  for select using (auth.uid() = user_id);
```

**Q.** 점검 항목은?

**A.**
- 모든 공개 테이블에 RLS가 켜져 있는가
- 클라이언트에 service_role 키가 들어 있지 않은가
- Storage 버킷이 의도 없이 공개돼 있지 않은가
- Firebase 규칙에 `allow read, write: if true`가 없는가

> **🧪 가설** "정책 작성보다 RLS 켜기를 잊는 경우가 더 흔하다." 검증: Supabase 대시보드 Advisors 경고 수를 센다.

출처: NVD/CVE 레코드 CVE-2025-48757(2025.5), Matt Palmer 스캔 관련 보도·분석(2025). CVE 레코드는 원문 확인, 170/1,645 수치는 2차 자료 기반.

## 3-7. 존재하지 않는 패키지를 AI가 권하면?

**Q.** AI가 `npm install some-helper`를 안내했는데 그런 패키지가 없다면?

**A.** 환각 패키지다. 문제는 공격자가 그 이름을 미리 등록해 악성 코드를 넣어 둘 수 있다는 점이다. Python Software Foundation의 Seth Larson이 이를 slopsquatting이라 불렀다.

> **⚠️ 실제 사례** Virginia Tech 등 연구진은 16개 코드 생성 모델로 Python·JavaScript 샘플 57만 6천 개를 만들어 분석했다. 논문 초록 기준 존재하지 않는 패키지 비율은 상용 모델 최소 5.2%, 오픈소스 모델 최소 21.7%였고(전체 약 19.7%로 보도), 고유 환각 이름은 205,474개였다. 환각 이름 중 43%는 같은 프롬프트를 10번 반복할 때마다 다시 나왔다. 반복되므로 공격자가 예측해 선점하기 쉽다는 뜻이다. 모델별 편차도 컸다.

**Q.** 처음엔 "오타를 조심하면 된다"고 생각하기 쉽다. 왜 틀렸나?

**A.** 보도에 따르면 가짜 이름 중 한 글자 오타는 약 13%뿐이었다. 대부분 그럴듯한 새 이름이라 눈으로 걸러내기 어렵다.

> **✅ 체크포인트** 새 패키지를 설치하기 전에 확인한다.
> - 공식 문서나 저장소가 그 이름을 직접 안내하는가
> - 등록일, 주간 다운로드, 관리자, 저장소 링크가 정상인가
> - 기존 의존성으로 해결되지 않는가

**Q.** 더 깊은 방어는?

**A.** lockfile 고정, 설치 스크립트 제한, SCA 도구는 Part 4에서 다룬다. 여기서는 "AI가 말한 이름은 검증 전까지 가설"이라는 습관만 기억한다.

출처: Spracklen 외, "We Have a Package for You!" (arXiv:2406.10279) 초록 확인(16개 모델·57.6만 샘플·205,474개·5.2%/21.7%). 19.7%·43%는 보도 기준.

## 3-8. 프롬프트로 보안 품질을 올릴 수 있나?

**Q.** "보안에 신경 써서 만들어줘"라고 하면 충분한가?

**A.** 부족하다. 모호한 요구는 모호한 결과를 낳는다. 검증 가능한 문장으로 쪼개서 명세에 넣어야 한다.

| 모호한 요청 | 검증 가능한 요구사항 |
|---|---|
| 안전하게 | 모든 SQL은 파라미터 바인딩만 사용 |
| 로그인 보호 | 주문 API는 `userId` 소유자 검사 필수 |
| 비밀 관리 | 키는 환경 변수만, 코드·로그에 출력 금지 |
| 에러 처리 | 사용자 응답에 스택트레이스 금지 |
| 패키지 | 새 의존성 추가 시 이름·이유를 먼저 보고 |

> **🧪 가설** "보안 요구사항을 명세에 넣으면 같은 모델도 취약 패턴이 줄어든다." 검증 설계: 같은 기능을 요구사항 없음/있음 두 조건으로 각 5회 생성하고, 3-2쪽 표로 채점해 평균 경고 수를 비교한다. 표본이 작으니 "경향" 이상으로 해석하지 않는다.

**Q.** 프롬프트만으로 끝나나?

**A.** 아니다. 프롬프트는 확률을 낮출 뿐 보증이 아니다. 따라서 같은 요구사항을 린터·SAST·테스트로 자동 검사해 두 번 걸러야 한다. 패키지 환각 연구에서도 프롬프트 기법을 조합한 완화 결과가 모델별로 달랐고, 저자들은 여전히 높다고 평가했다.

> **💡 PM 시선** 보안 요구사항은 "완료의 정의(DoD)"에 넣는 항목이다. 티켓 템플릿에 "인가 규칙 / 입력 검증 / 시크릿 / 로그" 네 줄을 고정하면 매번 다시 기억하지 않아도 된다.

## 3-9. 5분 보안 리뷰는 무엇을 보나?

**Q.** 코드를 못 읽는 사람도 할 수 있는 리뷰가 있나?

**A.** 있다. AI에게 diff를 요약시키되, 아래 질문에는 사람이 직접 답한다.

> **✅ 체크포인트 — 5분 보안 리뷰 (항목당 1분)**
> 1. **시크릿** `sk-`, `AKIA`, `password`, `.env` 검색. 코드·로그·클라이언트 번들에 키가 있는가
> 2. **경계** 새 라우트·폼·업로드마다 입력 검증이 있는가
> 3. **인가** 계정 두 개로 교차 접근을 시도했는가
> 4. **데이터** 쿼리가 파라미터화됐는가. RLS·버킷·규칙이 열려 있지 않은가
> 5. **설정·의존성** CORS `*`, 디버그 모드, 새 패키지의 이름·출처

**멈춤 신호:** 소유자 확인 없는 id 조회, 문자열 결합 쿼리, 이유 없이 추가된 의존성, 에러 시 내부 정보 응답.

> **🚫 흔한 착각** "AI에게 다시 검토시키면 충분하다." 같은 가정을 반복할 수 있다. 도구·규칙·사람 관점을 섞는다(Part 8).

> **🛠 실습** 작은 앱 하나로 5분 리뷰를 하고, 발견 항목을 심각도(상/중/하)와 담당자로 기록한다. PR마다 5개 항목 통과율을 남기면 월 단위로 효과를 데이터로 볼 수 있다.

> **🗣 토론** AI 코드의 취약점 책임은 모델사·도구·개발자·PM 중 누구인가? "인가 표" 작성 10분은 합리적인가?

> **📌 핵심 정리**
> - 연구 수치는 실험 조건과 함께 읽는다. 패턴은 시크릿·SQL 결합·인가 누락·CORS·검증·에러·설정 7가지다.
> - BaaS는 RLS·규칙이 곧 서버 보안이다. AI가 권하는 패키지는 검증 전까지 가설이다.
> - 프롬프트 요구사항 + 5분 리뷰 + 자동 도구로 이중 점검한다.
