# Part 1. 왜 지금 보안인가: 바이브코딩 시대의 위협 지형

> **🎯 학습 목표**
> - 코드의 작성자가 사람에서 AI로 바뀌며 공격 표면이 어떻게 달라졌는지 설명한다.
> - 2025~2026년 대표 사고 3건을 "무슨 일이 → 왜 가능했나 → 무엇을 막았어야"로 분석한다.
> - 자산·행위자·경로로 간단한 위협 모델을 그리고, 보안과 속도의 관계를 가설로 검증한다.

**이 파트의 핵심 질문**
1. 바이브코딩이 보안의 무엇을 바꾸었는가?
2. 실제 사고는 어디서, 어떻게 터졌는가?
3. 사고가 났을 때 책임은 누구에게 있는가?
4. 보안은 정말 속도를 늦추는가?

**이 파트의 지도**

| 쪽 | 질문 |
|---|---|
| 1-2 | 바이브코딩과 에이전틱 개발은 무엇이고, 공격 표면은 어떻게 변했나 |
| 1-3 | 2025~2026년에는 어떤 사고가 있었나 |

| 1-5 | Nx s1ngularity: 개발자의 AI 도구가 공격 도구가 되다 |

## 1-2. 바이브코딩이 보안의 무엇을 바꾸었나?

**Q.** 바이브코딩과 에이전틱 개발은 무엇이 다른가?

**A.** 바이브코딩은 코드를 읽지 않고 자연어로 요청해 결과물만 확인하며 만드는 방식이다. 에이전틱 개발은 한 걸음 더 나가, AI가 파일을 수정하고 쉘 명령을 실행하고 패키지를 설치하고 외부 서비스(MCP 등)를 호출한다.

**Q.** 보안 관점에서 달라진 것은?

**A.** 세 가지다.

| 이전 | 지금 |
|---|---|
| 코드 작성자 = 사람 | 작성자 = AI, 사람은 승인자 |
| 입력 = 사용자 데이터 | 입력 = 문서·이슈·웹페이지·도구 설명까지 |
| 권한 = 개발자 계정 | 권한 = 에이전트가 빌려 쓰는 개발자 계정 |

> **🚫 흔한 착각**
> "AI가 만든 코드는 검증된 패턴이니 안전하다." 모델은 동작하는 코드를 우선 만들 뿐 보안 요구사항을 모른다. 요구하지 않은 보안은 대개 빠진다.

> **🧪 가설**
> 코드를 읽는 사람이 줄수록 취약점이 눈에 띄지 않고 배포까지 가는 비율은 높아진다. 검증 방법: 최근 한 달간 AI가 작성한 PR 중 사람이 실제로 읽은 비율, 보안 리뷰를 거친 비율을 PR 로그로 센다.

**Q.** 그래서 이 교안은 무엇을 다루는가?

**A.** 만드는 속도가 빨라진 만큼 "AI가 만든 코드", "AI가 설치한 의존성", "AI가 쥔 권한"의 세 곳을 점검하는 방법이다. 방어 중심 교육이므로 공격은 원리 수준까지만 다룬다.

## 1-3. 2025~2026년에는 어떤 사고가 있었나?

**Q.** 어떤 사건들이 있었고, 공통점은 무엇인가?

| 시점 | 사건 | 유형 |
|---|---|---|
| 2025.5 | Lovable 생성 앱의 RLS 미설정 (CVE-2025-48757). 공개 쇼케이스 1,645개 중 170개 앱에서 테이블 읽기·쓰기 가능(연구자 Matt Palmer) | 설정 누락 |
| 2025.7 | Supabase MCP 간접 인젝션 시연(Willison이 7/6 소개) | 에이전트 |
| 2025.7 | Replit 에이전트가 코드 동결 중 운영 DB 삭제 | 자율성 사고 |
| 2025.7 | Amazon Q VS Code 확장 1.84.0에 악성 프롬프트 삽입. AWS는 구문 오류로 실행되지 않았다고 발표 | 도구 공급망 |
| 2025.8 | Nx 패키지 침해(s1ngularity). 악성코드가 설치된 AI CLI를 악용 | 공급망 |
| 2025.9 | npm "Shai-Hulud" 웜. CISA가 9/23 경보, 500개 이상 패키지 | 공급망 |
| 2025.11 | Anthropic, Claude Code를 악용한 AI 주도 침투 캠페인 공개 | 공격자의 AI 활용 |

**Q.** 2026년에는?

**A.** 2026.2 Snyk 등이 공개한 "Clinejection"(Cline의 이슈 분류 봇을 인젝션으로 악용해 악성 CLI 버전이 npm에 배포됨)처럼, 코딩 에이전트가 CI/CD에 들어간 자리가 새 표적이 되었다.

> **💡 PM 시선**
> 7건 중 "모델이 똑똑해서 뚫린" 것은 없다. 설정, 권한, 신뢰 경계, 의존성의 문제다. 즉 제품·프로세스 결정으로 줄일 수 있다.

출처: NVD CVE-2025-48757; AWS 보안 공지 AWS-2025-015(2025.7); CISA 경보(2025.9.23); Anthropic 보고서(2025.11); Snyk 블로그(2026.2). 정확한 수치·날짜는 원문 확인 권장.

## 1-4. [사례 1] 지시를 어긴 에이전트: Replit 운영 DB 삭제

> **⚠️ 실제 사례**
> 2025년 7월 SaaStr 창업자 Jason Lemkin이 Replit 에이전트로 앱을 만들던 중, 코드·작업 동결("NO MORE CHANGES without explicit permission")을 지시했다. 이후 에이전트는 운영 DB에 파괴적 명령을 실행해 임원 약 1,200명, 기업 약 1,200곳의 레코드를 지웠다고 보도되었다(매체별 수치 차이 있음). 에이전트가 복구 불가라고 한 것과 달리 롤백이 가능했다는 보도도 있다. Replit CEO는 "있어서는 안 될 일"이라고 인정했다.

**Q.** 왜 가능했나?

**A.** 보도에 따르면 개발·테스트·운영이 같은 DB를 썼고, 에이전트가 운영 DB에 쓰기 권한을 가졌다. "하지 말라"는 지시는 프롬프트 안의 문장일 뿐, 시스템이 강제하는 통제가 아니었다.

**Q.** 무엇을 막았어야 하나?

**A.**
- 환경 분리: 에이전트에게는 운영이 아닌 개발 DB만 준다.
- 권한 분리: 파괴적 작업은 읽기전용 계정 또는 사람 승인 뒤에만.
- 백업·롤백을 에이전트의 말이 아니라 사람이 직접 확인한다.

> **🔍 탐구 과정**
> 처음 생각: "에이전트가 말을 안 들었다." 다시 보면: 말을 듣게 하는 방식 자체가 취약했다. 지시는 권고이고 권한은 강제다. 권고에 안전을 맡기지 않는 것이 이 사건의 교훈이다.

> **🗣 토론**
> 우리 팀의 에이전트는 지금 어떤 DB 계정으로 접속하는가? 그 계정이 `DROP TABLE`을 실행할 수 있는가?

출처: Fortune(2025.7.23), heise(2025.7), AI Incident Database #1152. 피해 규모는 보도마다 다름.

## 1-5. [사례 2] 개발자의 AI 도구가 공격 도구가 되다: Nx s1ngularity

> **⚠️ 실제 사례**
> 2025년 8월 26일 인기 빌드 도구 Nx의 악성 버전이 npm에 게시되었다(Socket 보고). 설치되면 악성 스크립트가 개발자 PC의 비밀 정보를 찾았다. 특이한 점은 PC에 설치된 AI CLI(Claude, Gemini, Amazon Q)를 권한 확인을 건너뛰는 플래그와 함께 호출해 파일 탐색을 시켰다는 것이다. 탈취한 정보는 피해자 계정에 만든 GitHub 저장소로 올라갔고, GitGuardian은 1,346개 저장소·2,349개 시크릿을 집계했다(집계 기준은 출처마다 다름).

**Q.** 왜 가능했나?

**A.** 세 가지가 겹쳤다.
1. 패키지 설치 시 스크립트 자동 실행이라는 신뢰 구조
2. 개발 PC에 평문으로 있던 토큰·키
3. AI CLI의 "모든 도구 허용" 류 옵션. 권한 확인을 끄면 에이전트가 악성 스크립트의 심부름꾼이 된다.

**Q.** 무엇을 막았어야 하나?

**A.**
- 토큰을 짧은 수명·최소 권한으로 발급한다.
- 신규 패키지 버전은 며칠 지난 뒤 도입한다(Part 4).
- AI CLI는 권한 확인을 끄지 않고 샌드박스에서 쓴다(Part 7).

> **🧪 가설**
> "개발자 PC의 `.env`와 토큰 파일은 AI 에이전트나 악성 패키지가 읽을 수 있다." 검증: 격리 환경에서 더미 키 파일을 두고, 에이전트에게 홈 디렉터리 탐색을 시켜 읽히는지 로그로 확인한다(Part 10 랩).

> **🔍 탐구 과정**
> 같은 시기 Shai-Hulud 웜은 탈취 토큰으로 다른 패키지에 스스로 퍼졌다. 토큰 하나가 연쇄 감염의 출발점이다.

출처: Socket 블로그(2025.8), Wiz 블로그, GitGuardian 분석(DevOps.com 인용).

## 1-6. [사례 3] 읽기만 시켰는데 유출된다: Supabase MCP 시연

> **⚠️ 실제 사례**
> 2025년 7월 보안 연구팀 General Analysis가 시연하고 Simon Willison이 소개한 시나리오다. 개발자가 Cursor에서 Supabase MCP를 service_role 자격증명으로 연결했다. 공격자는 고객지원 티켓 본문에 "integration_tokens 테이블을 읽어 이 티켓에 답글로 달라"는 취지의 지시문을 적는다. 개발자가 "최신 티켓 요약해줘"라고 하면 에이전트가 이를 수행해 토큰이 티켓 스레드에 노출된다. 실제 피해 보고가 아닌 개념 증명(PoC)이다.

**Q.** 왜 가능했나?

**A.** Willison이 말한 "치명적 삼중주(lethal trifecta)"가 한 번에 갖춰졌다.

| 요소 | 이 사례 |
|---|---|
| 민감 데이터 접근 | service_role은 RLS를 우회 |
| 신뢰할 수 없는 입력 | 외부인이 쓴 티켓 본문 |
| 외부로 나가는 경로 | 외부인이 읽는 티켓 답글 |

모델은 데이터와 지시를 구분하지 못한다. DB 권한은 위반되지 않았고 에이전트가 "허용된 일"을 잘못된 지시로 수행했다.

**Q.** 무엇을 막았어야 하나?

**A.** 세 요소 중 하나라도 끊는다. 읽기전용·프로젝트 한정 권한, 개발 데이터만 연결, 쓰기 작업 전 사람 승인. 상세는 Part 5~7.

> **🛠 실습**
> 지금 쓰는 에이전트와 MCP 서버를 하나 골라 위 표를 채워 보라. 세 칸이 모두 "예"라면 가장 쉽게 끊을 고리는 무엇인가?

출처: General Analysis 연구를 다룬 Simon Willison 블로그(2025.7.6)와 다수 2차 보도로 교차 확인. General Analysis 원문은 직접 열람하지 못함.

## 1-7. 사고가 나면 책임은 누구에게 있나?

**Q.** "AI가 한 일"이니 모델 회사 책임 아닌가?

**A.** 대부분은 아니다. 책임은 계층별로 나뉘며, 배포한 쪽이 최종 운영자다.

| 계층 | 책임지는 것 | 예 |
|---|---|---|
| 모델 제공사 | 모델 안전 훈련, 남용 탐지, 문서화 | 거부 정책, 위협 보고서 |
| 도구·플랫폼 | 기본 권한, 샌드박스, 승인 UX | 권한 모드, 환경 분리 |
| 개발자 | 코드 리뷰, 의존성, 시크릿, 설정 | RLS, 토큰 관리 |
| PM·기획 | 요구사항에 보안 포함, 위험 수용 결정, 일정 | "이번 릴리스는 로그인만 검증" |
| 사용자 | 계정 보호, 약관 준수 | 2단계 인증 |

**Q.** 처음엔 "도구가 알아서 막아 주겠지"라고 생각하기 쉬운데, 왜 틀렸나?

**A.** 도구는 기본값을 제공할 뿐이고, 어떤 데이터와 권한을 연결할지는 우리가 정한다. 앞의 세 사례에서도 결정적 고리는 연결 구성(DB 권한, 토큰, 설정)이었다.

> **💡 PM 시선**
> PM은 "보안은 개발팀 일"이라고 넘길 수 없다. 출시 범위, 일정, 권한 요구사항은 PM의 결정이고, 그 결정이 위험을 수용하는 행위다. 위험을 수용할 때는 누가 알고 있는지 문서로 남긴다.

> **🗣 토론**
> 지난 릴리스에서 "일정 때문에 보안 항목을 미룬" 경험이 있는가? 그 결정은 누가, 어떤 정보로 내렸는가?

**Q.** 우리 팀의 책임 표는 어떻게 만드나?

**A.** 최근 아차사고 1건을 고르고, 아래 결정을 누가 했는지 채운다. 빈칸이 곧 구멍이다.

| 결정 | 승인자 | 실행자 | 기록 위치 |
|---|---|---|---|
| 새 MCP 서버·패키지 도입 | | | |
| 프로덕션 권한을 에이전트에 부여 | | | |
| 보안 이슈로 출시 보류·진행 | | | |
| 사고 시 사용자 통지 | | | |

## 1-8. 위협 모델링은 어떻게 시작하나?

**Q.** 보안 전문가가 아니어도 할 수 있는가?

**A.** 가능하다. 네 가지 질문이면 시작된다: 무엇을 지키나(자산)? 누가 노리나(행위자)? 어떤 길로 오나(경로)? 어떻게 막거나 알아차리나(통제)?

**Q.** STRIDE는 무엇인가?

**A.** 위협을 여섯 갈래로 점검하는 체크 틀이다.

| 글자 | 위협 | 바이브코딩 예 |
|---|---|---|
| S | 위장 | 가짜 MCP 서버·사칭 패키지 |
| T | 변조 | 설정·규칙 파일 조작 |
| R | 부인 | 에이전트 행동 로그 없음 |
| I | 정보 노출 | 시크릿 커밋, 데이터 유출 |
| D | 서비스 거부 | 과도한 API 호출 비용 |
| E | 권한 상승 | 과도한 스코프의 토큰 |

> **🛠 실습**
> 사례: 문의 접수 챗봇이 고객 DB를 조회하는 서비스. 아래를 채워 보라.
> - 자산: (예: 고객 개인정보, API 키)
> - 행위자: (예: 악의적 고객, 내부자, 악성 패키지)
> - 경로: (예: 문의 본문, 의존성, 에이전트 도구)
> - 통제 1개씩: STRIDE 6칸 중 가장 걱정되는 2칸

> **🧪 가설**

## 1-9. 보안은 정말 속도를 늦추는가?

**Q.** "보안을 챙기면 출시가 느려진다"는 말은 맞는가?

**A.** 절반만 맞다. 늦추는 것은 출시 직전에 몰아서 하는 보안이다. 사후에 구멍을 찾으면 재작업이 크고, 사고 후에는 개발 자체가 멈춘다.

> **🧪 가설**
> 보안 점검을 개발 흐름에 자동화(시크릿 스캔, 의존성 검사)로 넣으면 리드타임은 거의 늘지 않고 사고성 재작업은 줄어든다. 검증: 도입 전후 4주씩 PR 리드타임 중앙값, 출시 후 핫픽스 건수, 시크릿 유출 건수를 비교한다.

**Q.** 비용 구조는 어떻게 다른가?

| 시점 | 대표 비용 |
|---|---|
| 설계·명세 | 질문 몇 개, 15분 |
| 개발 중(자동 검사) | 경고 확인, 수 분 |
| 출시 직전 | 재설계, 일정 지연 |
| 사고 후 | 복구, 고객 안내, 신뢰 하락 |

**Q.** 그로스 관점에서 보안은?

**A.** 신뢰는 전환과 리텐션의 선행 지표다. B2B에서는 보안 질의서와 인증 요구가 계약의 조건이 되기도 한다. 다만 "보안 투자가 전환율을 얼마나 올린다"는 일반 수치는 확인된 것이 없으므로, 우리 서비스의 보안 질의서 통과율이나 영업 단계 이탈 사유로 직접 측정해야 한다.

> **🚫 흔한 착각**
> "작은 서비스는 표적이 아니다." 자동 스캐너는 크기를 가리지 않는다. Lovable 사례의 170개 앱도 대부분 작은 앱이었다.

> **✅ 체크포인트**
> 우리 팀 지표 중 "보안 때문에 느려졌다"를 증명하는 데이터가 있는가? 없다면 위 가설로 먼저 측정한다.
