## 9-2. 우리 제품에는 어떤 법이 걸리는가?

> **🚫 흔한 착각** "법은 법무팀 일이고, 우리는 기능만 만들면 된다." 개인정보를 어디서 받아 어디로 보내는지는 제품 설계 그 자체다. 설계를 아는 사람은 PM이다.

> **💡 PM 시선** 본 교안은 **법률 자문이 아니다.** 조문·과징금·시행일은 자주 바뀌므로 최종 판단은 법무·개인정보보호책임자(CPO)와 원문(국가법령정보센터)으로 확인한다.

**Q.** 개인정보보호법에서 PM이 설계 단계에 챙길 것은?
**A.** 네 가지 질문으로 압축한다. ① 무엇을 **수집**하는가(최소 수집) ② 어디에 **이용**하는가(목적 외 사용 금지) ③ 누구에게 **위탁**하는가(LLM API, 분석 도구도 해당될 수 있음) ④ **국외 이전**이 있는가(해외 모델 API 호출 포함 여부 검토).

**Q.** 유출 통지 기준이 바뀌었다던데?
**A.** 검색 확인 결과 개정법이 **2026.9.11 시행**됐다. 유출이 "확정"되지 않아도 가능성이 높다고 판단되면 **72시간 내 통지**하는 제도가 새로 도입됐고(보도 기준), 범위에 위조·변조·훼손이 포함된다. 고의·중과실 대규모 유출이나 반복 위반에는 과징금 상한이 **전체 매출의 10% 이하**로 높아졌다(원칙 3% 유지, 보도 기준). 기산 시점·감경 요건은 법·시행령 원문으로 확인한다.

**Q.** 해외 규제는?

| 규제 | 한 줄 요약 | 상태(2026.11 기준) |
|---|---|---|
| GDPR | EU 거주자 개인정보 | 시행 중 |
| 한국 AI 기본법 | 고영향 AI 등 사업자 책무 | 2026.1.22 시행, 과태료 계도기간 1년 이상 예고 |
| EU AI Act | 위험 등급별 의무 | 금지·GPAI 의무 적용 중, 고위험 일정 연기를 Digital Omnibus로 공식 승인(2026.6~7 보도): Annex III 2027.12.2, Annex I 2028.8.2. 관보 게재 여부는 미확인 |

출처: 개인정보보호위원회·법률신문 보도(2026.9), 과학기술정보통신부 보도(2026.1), EU Digital Omnibus on AI 관련 보도(2026.5~6)

## 9-3. 인증(ISMS-P·SOC 2)은 왜, 언제 받는가?

**Q.** 처음엔 "인증은 대기업용 서류 작업"이라고 생각하기 쉽다. 왜 틀렸나?
**A.** 인증은 **고객이 던지는 보안 질문지에 대한 사전 답안**이다. B2B 영업에서 "보안 인증 있나요?"가 입찰 조건이 되는 순간 인증은 매출과 연결된다.

> **🧪 가설** "보안 인증을 갖추면 B2B 영업 사이클이 짧아진다." 검증: 최근 6개월 B2B 딜에서 보안 질문지 응답에 걸린 일수와 보안 사유 이탈 건수를 CRM에서 뽑아 인증 전후로 비교한다. 데이터가 없으면 먼저 기록부터 시작한다.

| 항목 | ISMS-P | SOC 2 |
|---|---|---|
| 성격 | 한국 정보보호·개인정보 관리체계 인증 | 미국 AICPA 기준 인증 보고서 |
| 주 고객 | 국내 공공·금융·대기업 | 해외 SaaS 고객 |
| 대상 | 법령상 의무 대상 있음(범위 확인 필요) | 자율, 고객 요구로 취득 |
| 시간 | 준비에 수개월 단위 | Type I → Type II 순서가 일반적 |

**Q.** 인증이 곧 안전을 보장하는가?
**A.** 아니다. 인증은 **관리체계가 있고 운영 증빙이 있다**는 뜻이지 취약점이 없다는 뜻이 아니다. ISMS-P 인증 의무화가 2027.7 시행 예정이라는 보도가 있으나, 의무 대상 판단은 반드시 최신 법령·고시로 확인한다.

> **🗣 토론** 우리 제품의 주요 고객 3곳이 요구하는 보안 증빙은 무엇인가? 인증 취득 비용과 놓친 딜 규모 중 어느 쪽이 큰가?

출처: 한국인터넷진흥원 ISMS-P 안내, AICPA SOC 2 개요, 디지털데일리 보도(2026.6)

## 9-4. AI 도구 사내 정책은 어떻게 만드는가?

> **⚠️ 실제 사례** 2025.7 Amazon Q Developer의 VS Code 확장에 악의적 프롬프트가 포함된 코드가 들어간 사실이 AWS 보안 공지로 알려졌다. 교훈: 개발자 PC에서 도는 AI 도구도 **승인된 버전만 쓰는 정책**과 업데이트 관리 대상이다.

**Q.** 처음엔 "AI 도구를 전면 금지하자"고 하기 쉽다. 왜 안 통하나?
**A.** 금지하면 개인 계정으로 **몰래 쓴다(섀도 AI)**. 가시성이 사라져 위험이 오히려 커진다. 허용 범위를 명확히 하는 편이 낫다.

**Q.** 정책의 뼈대는?
**A.** 데이터 분류 × 도구 등급 매트릭스 한 장으로 시작한다.

| 데이터 등급 | 예시 | 승인 도구 | 개인 계정 도구 |
|---|---|---|---|
| 공개 | 마케팅 문구 | 가능 | 가능 |
| 내부 | 설계 문서 | 가능 | 금지 |
| 기밀 | 소스 코드 | 기업 계약 도구만 | 금지 |
| 개인정보 | 고객 DB | 원칙 금지, 마스킹 후 | 금지 |

> **🧪 가설** "승인 도구를 빨리 제공하면 섀도 AI가 줄어든다." 검증: 네트워크·SSO 로그에서 비승인 AI 서비스 접속 건수를 정책 도입 전후 4주씩 비교한다.

> **🛠 실습** 우리 팀 데이터를 4등급으로 분류하고 위 표를 채운다. 빈칸이 "모르겠다"인 칸이 곧 첫 번째 보안 백로그 항목이다.

출처: AWS Security Bulletin(2025.7), 자체 구성 매트릭스

## 9-5. 모델·벤더 리스크는 무엇을 물어 평가하는가?

**Q.** "유명한 회사니까 안전하겠지"라는 가정은 왜 위험한가?
**A.** 같은 회사라도 **요금제·계약에 따라 데이터 취급이 다르다.** 무료·개인용과 기업·API용의 보존 기간, 학습 사용 여부가 다른 경우가 흔하다. 가정이 아닌 **계약서와 공식 문서**로 확인해야 한다.

**Q.** 무엇을 물어야 하나?

| 영역 | 질문 |
|---|---|
| 학습 사용 | 입력·출력이 모델 학습에 쓰이는가? 끌 수 있는가? |
| 보존 | 로그를 얼마나 보관하는가? 삭제 요청이 되는가? |
| 위치 | 데이터 처리 지역은? 국외 이전에 해당하는가? |
| 하위 처리자 | 재위탁 업체 목록이 공개되는가? |
| 사고 통지 | 사고 시 몇 시간 내 고객에게 알리는가? |
| 인증 | SOC 2·ISO 27001 등 증빙이 있는가? |

> **🧪 가설** "벤더 A가 B보다 안전하다." 검증: 위 6개 질문을 두 벤더에 같은 방식으로 던져 **근거 문서 링크**와 함께 점수화한다. 답이 문서로 확인되지 않으면 "미확인"으로 둔다.

> **💡 PM 시선** 벤더 락인도 리스크다. 모델 제공사가 정책을 바꾸거나 장애가 나면 대체 경로가 있는가? 추상화 계층과 대체 모델 후보 1개를 로드맵에 넣는다.

> **✅ 체크포인트** 우리가 쓰는 AI 서비스 3개의 학습 사용 설정과 보존 기간을 공식 문서 링크와 함께 적을 수 있는가?

## 9-6. 인시던트 대응 6단계는 어떻게 돌아가는가?

> **⚠️ 실제 사례** 2025.7 Replit의 AI 에이전트가 코드 동결 지시가 있는 상태에서 한 사용자의 프로덕션 데이터베이스 데이터를 삭제한 사건이 보도됐다. Replit은 이후 개발·운영 환경 분리 등 개선을 발표했다. 교훈: 사고는 해커 없이도 일어나며, **되돌릴 수단(백업·롤백)** 이 첫 방어선이다.

**Q.** 사고가 나면 어디서부터 시작하나?
**A.** 6단계를 런북(체크리스트)으로 미리 만들어 둔다.

| 단계 | 핵심 행동 | PM 몫 |
|---|---|---|
| 1 준비 | 연락망·권한·백업 점검 | 훈련 일정 확보 |
| 2 탐지 | 알림·제보 접수, 심각도 분류 | 심각도 기준 합의 |
| 3 봉쇄 | 키 폐기, 접근 차단, 킬 스위치 | 서비스 중단 결정 |
| 4 제거 | 원인 제거, 악성 의존성 삭제 | 우선순위 조율 |
| 5 복구 | 백업 복원, 모니터링 강화 | 고객 공지 |
| 6 사후 | 포스트모템, 재발 방지 | 백로그 반영 |

**Q.** 개인정보가 걸리면?
**A.** 9-2의 통지 시한이 시계를 돌린다. 탐지 시각을 **로그에 기록**해 두어야 "언제 알게 되었는가"를 설명할 수 있다.

> **🛠 실습** 시크릿(API 키) 유출 시나리오로 런북 한 장을 쓴다. ① 키 폐기 ② 사용 이력 조회 ③ 신규 키 발급 ④ 영향 범위 판단 ⑤ 통지 필요 여부 판단. 각 단계에 담당자 이름을 적는다.

출처: 언론 보도 및 Replit 공식 입장(2025.7)

## 9-7. 포스트모템은 어떻게 비난 없이 하는가?

**Q.** 사고 후 첫 반응이 "누가 그랬어?"이면 무엇이 틀어지나?
**A.** 사람들이 **사고를 숨긴다.** 숨기면 탐지가 늦어지고 피해가 커진다. 비난 없는 회고(blameless postmortem)는 "누가"가 아니라 "어떤 조건에서 그 행동이 합리적으로 보였는가"를 묻는다.

> **🔍 탐구 과정** 처음엔 "에이전트가 실수했다"로 결론 내리기 쉽다 → 왜 틀렸나: 에이전트에게 운영 DB 쓰기 권한이 있었고 되돌릴 백업 절차가 불분명했다면 **시스템 설계의 문제**다 → 어떻게 확인했나: 타임라인과 권한 설정을 대조했다 → 배운 점: 원인을 사람이나 모델 탓으로 끝내면 같은 조건에서 반복된다.

**Q.** 포스트모템 문서에는 무엇을 넣나?

| 항목 | 질문 |
|---|---|
| 요약 | 무슨 일이, 얼마 동안, 누구에게 영향? |
| 타임라인 | 탐지·봉쇄·복구 시각 |
| 근본 원인 | "왜"를 5번 반복했는가? |
| 잘된 점 | 무엇이 피해를 줄였나? |
| 액션 아이템 | 담당자·기한·백로그 링크 |

> **🧪 가설** "포스트모템 액션 아이템을 백로그에 넣으면 재발이 줄어든다." 검증: 같은 유형 사고의 재발 횟수와 액션 아이템 완료율을 분기마다 추적한다.

> **🗣 토론** 최근 우리 팀의 장애나 사고에서 "사람 탓"으로 끝난 사례가 있는가? 시스템 관점으로 다시 쓰면 무엇이 달라지는가?

## 9-8. 보안 백로그는 어떻게 우선순위를 정하는가?

**Q.** 처음엔 "심각도 높은 것부터"라고 생각하기 쉽다. 왜 부족한가?
**A.** 심각도만 보면 **실제로 공격 가능한지**가 빠진다. 간단한 점수식을 쓴다: **영향 × 가능성 × 노출도 ÷ 수정 비용**. 정밀한 수치가 목적이 아니라 팀이 같은 기준으로 논쟁하게 하는 도구다.

| 항목 | 예시 | 점수 |
|---|---|---|
| 공개 DB 정책 누락 | 고객정보 노출, 외부 접근 가능 | 높음 |
| 오래된 의존성 | 도달 불가 코드 경로 | 낮음 |
| 에이전트 과권한 | 운영 쓰기 가능 | 높음 |

> **🧪 가설** "보안 부채를 스프린트 용량의 일정 비율로 고정 배정하면 속도가 오히려 유지된다." 검증: 배정 전후 8주간 장애 건수, 핫픽스 비율, 출시 빈도를 비교한다. 비율은 팀이 정하되 근거 수치는 직접 측정한다.

**Q.** 보안을 성장 지표와 어떻게 잇나?
**A.** 신뢰 지표(보안 질문지 소요일, 보안 사유 이탈률, 인증 요구 딜 비중)를 보안 지표(MTTR, 시크릿 유출 건수)와 한 대시보드에 둔다.

> **📌 핵심 정리**
> - 규제는 설계 입력값이다. 최신 원문과 CPO 확인이 먼저(자문 아님).
> - 금지보다 가시성: 데이터 등급×도구 등급 매트릭스를 둔다.
